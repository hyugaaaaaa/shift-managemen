# 企業単位データ管理実装計画書

## 1. 概要
本システムのデータを企業（テナント）単位で保存・管理できるようにするための改修計画です。
現状のシングルテナント構成から、複数の企業が1つのシステムを利用できるマルチテナント構成（論理分離方式）への移行を行います。

## 2. データベース設計変更

### 2.1 新規テーブル作成
企業情報を管理する `companies` テーブルを作成します。ユニークな `company_code` を持たせます。

```sql
CREATE TABLE `companies` (
  `company_id` INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `company_name` VARCHAR(100) NOT NULL,
  `company_code` VARCHAR(20) NOT NULL UNIQUE, -- 招待コード（例: EMP12345）
  `representative_name` VARCHAR(100),
  `address` VARCHAR(255),
  `phone_number` VARCHAR(20),
  `created_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`company_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 2.2 既存テーブルへの変更
各データがどの企業に属するかを識別するため、主要テーブルに `company_id` を追加、または紐付けを行います。

#### `users` テーブル
ユーザーがどの企業に属するかを定義します。また、**メールアドレスのユニーク制約を企業単位に変更**します。

```sql
ALTER TABLE `users` ADD COLUMN `company_id` INT UNSIGNED NOT NULL AFTER `user_id`;
ALTER TABLE `users` ADD CONSTRAINT `fk_users_company` FOREIGN KEY (`company_id`) REFERENCES `companies`(`company_id`) ON DELETE CASCADE;

-- メールアドレスのユニーク制約変更（掛け持ち対応）
-- 既存のユニークインデックスを削除し、(email, company_id) の複合ユニークインデックスを作成
ALTER TABLE `users` DROP INDEX `email`;
ALTER TABLE `users` ADD UNIQUE KEY `unique_email_company` (`email`, `company_id`);

-- 利用規約同意記録用カラム
ALTER TABLE `users` ADD COLUMN `is_agreed_terms` TINYINT(1) NOT NULL DEFAULT 0;
ALTER TABLE `users` ADD COLUMN `agreed_terms_at` DATETIME DEFAULT NULL;
```

#### `password_resets` テーブル
どの企業のパスワードをリセットするためのトークンかを識別するために `company_id` を追加します。

```sql
ALTER TABLE `password_resets` ADD COLUMN `company_id` INT UNSIGNED NOT NULL AFTER `email`;
-- 複合インデックス等は必要に応じて調整
```

#### `system_settings` テーブル
システム設定（締め日、給料日など）を企業ごとに保持できるように変更します。

```sql
ALTER TABLE `system_settings` ADD COLUMN `company_id` INT UNSIGNED NOT NULL DEFAULT 0 FIRST; -- 0はシステム全体設定用、または既存データ移行用
-- Primary Keyの変更
-- ALTER TABLE `system_settings` DROP PRIMARY KEY, ADD PRIMARY KEY (`company_id`, `setting_key`);
```

以下のテーブルは `users` テーブルと紐付いているため、直接 `company_id` を持たせる必要はありませんが、クエリのパフォーマンスや将来的な独立性を考慮して追加することも検討します。（今回は `users` 経由での参照を基本とします）
- `shifts_requested`
- `shifts_scheduled`
- `attendance_records`
- `user_skills`
- `operation_logs`

## 3. アプリケーションロジック変更

### 3.1 画面・登録フローの構成変更
明確に役割を分けた3つの画面（URL）を用意します。

**1. ログイン画面 (`index.php` / `login.php`)**
- 既存のログインフォーム（メールアドレス・パスワード）。
- 全ユーザー（オーナー・アルバイト）共通の入り口。
- 画面下部に以下の新規登録へのリンクを配置。
    - 「企業アカウントを新規作成する（オーナーの方）」
    - 「アルバイトとして登録する（招待コードをお持ちの方）」

**2. 新規企業登録画面 (`register_company.php`)**
- フォーム項目:
    - 企業名（必須）
    - 代表者氏名
    - オーナーユーザー名
    - メールアドレス
    - パスワード
- 処理:
    - `companies` レコード作成（`company_code` 自動生成）。
    - オーナーの `users` レコード作成。
    - 完了画面で「招待コード」を表示。

**3. 新規アルバイト登録画面 (`register_staff.php`)**
- フォーム項目:
    - **招待コード（必須）**
    - ユーザー名
    - メールアドレス
    - パスワード
- 処理:
    - 入力された `company_code` を検証。
    - 存在すれば、その `company_id` で `users` レコードを作成。
    - デフォルト権限は `part-time`。

### 3.2 ログイン認証・パスワードリセット
- **ログイン**: ログイン時にユーザー情報を取得する際、そのユーザーが所属する `company_id` をセッションに保存。
- **[追加] パスワードリセット (`forgot_password.php`)**:
    - メールアドレス送信時、そのアドレスで登録されている全ての企業 (`users`) を検索。
    - 企業ごとにリセットトークンを生成し、メール本文にそれぞれの企業名とリセット用URLを列記して送信。
- **[追加] パスワードリセット実行 (`reset_password.php`)**:
    - トークンに紐づく `company_id` のユーザーのパスワードのみを更新。

### 3.3 利用規約・プライバシーポリシー
- **[追加] 登録画面 (`register_company.php`, `register_staff.php`)**:
    - 「利用規約とプライバシーポリシーに同意する」チェックボックスを追加（必須）。
    - 各ドキュメントへのリンク（別タブで開く）を設置。
    - 登録処理時に同意日時を記録。
- **[追加] 規約ページ**: 静的ページとして作成、またはモーダル表示。

### 3.3 データアクセスのスコープ制御
- `functions.php` や各Viewでのデータ取得クエリにおいて、必ず `WHERE company_id = ?` (または `JOIN users ... WHERE users.company_id = ?`) を付与し、他企業のデータへアクセスできないように制限します。

### 3.4 既存システム設定の分離・管理画面改修
- `system_settings` を取得する関数を改修し、セッション内の `company_id` にリクエストされた設定値を返すように変更します。
- **[追加] オーナー管理画面 (`views/owner/system_settings_view.php` 等) に「企業情報」セクションを追加。**
    - 自分の企業の `company_code` を常時確認できるように表示。
    - 「招待コードをコピー」などのボタンを配置しやすくする。
    - **[追加] 「招待コードを再発行する」ボタンを設置。**
      - 流出時などのために、ボタン押下で新しいコードを生成しDBを更新する機能。
    - 必要に応じてダッシュボードにも表示。

## 4. 移行（マイグレーション）手順

現在運用中のデータがある場合、以下の手順で移行を行います。

1. **デフォルト企業の作成**:
   - `companies` テーブルに「デフォルト企業（例: 未設定株式会社）」を1レコード作成。
2. **既存データの紐付け**:
   - 既存の全 `users` レコードの `company_id` カラムを、作成したデフォルト企業のIDで更新。
   - 既存の `system_settings` をデフォルト企業IDに紐付け。

## 5. スケジュール

1. **DBスキーマ定義**: データベース変更スクリプトの作成
2. **バックエンド実装**: 登録・ログイン・共通関数の改修
3. **フロントエンド実装**: 登録画面フォームの修正
4. **テスト**: 複数アカウントを用いたデータ分離の検証
