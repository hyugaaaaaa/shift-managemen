# システム技術評価と改善提案書

## 1. 概要
本ドキュメントは、現在の「アルバイトシフト管理システム」のソースコードおよびアーキテクチャを、プロフェッショナルなシステムエンジニアの視点から評価し、品質・セキュリティ・保守性を向上させるための具体的な改善案をまとめたものです。

## 2. 総合評価
**評価ランク: B (標準的)**
小規模な業務システムとして必要な機能は網羅されており、基本的なセキュリティ対策（SQLインジェクション対策、CSRF対策、権限管理）も実装されています。MVC（Model-View-Controller）に近い構成でロジックと表示が分離されており、可読性は一定レベル保たれています。
しかし、将来的な機能拡張やチーム開発を見据えると、コードの構造化や設定管理、エラーハンドリングにおいて改善の余地があります。

## 3. 良い点 (Good Points)
*   **基本セキュリティの確保**: すべてのDB操作にPDOプリペアドステートメントを使用しており、SQLインジェクションのリスクが低い。また、独自実装ながらCSRFトークンによる対策が行われている。
*   **ロジックと表示の分離**: PHPのロジック処理（Controller）とHTML表示（View）が別ファイルに分割されており、デザイナーとエンジニアの分業が可能。
*   **トランザクション管理**: ユーザー削除処理などでトランザクション（`beginTransaction`, `commit`）が適切に使用されており、データ整合性が考慮されている。
*   **モダンなUI**: Bootstrap 5を採用し、レスポンシブ対応やインタラクティブなUIが実装されている。

## 4. 課題と改善提案

### 4.1 セキュリティと設定管理 (Critical)
| 課題 | 詳細 | 改善提案 |
| :--- | :--- | :--- |
| **認証情報のハードコード** | `config.php` にDB接続情報やSMTPパスワードが直書きされている。Git等で管理した場合、情報漏洩のリスクがある。 | 環境変数（`.env`ファイル）を使用し、`vlucas/phpdotenv` などのライブラリで読み込む方式に変更する。 |
| **セッションセキュリティ** | セッションクッキーの設定（`HttpOnly`, `Secure`, `SameSite`）が明示的でない。 | `session_start()` 前に `session_set_cookie_params()` でセキュアな設定を強制する。 |

### 4.2 アーキテクチャとコード品質 (Should Fix)
| 課題 | 詳細 | 改善提案 |
| :--- | :--- | :--- |
| **「神関数」ファイルの存在** | `functions.php` にDBアクセス、日付計算、メール送信など無関係なロジックが混在している。保守性が低い。 | クラスベースの設計に移行する（例: `Auth`クラス, `ShiftManager`クラス, `Mailer`クラス）。 |
| **エラーハンドリングの弱さ** | エラー発生時に `echo` や `die()` で画面に直接エラーを出している箇所があり、ユーザー体験とセキュリティによくない。 | 共通のエラーハンドリング機構を導入し、ユーザーには親切なメッセージを表示し、詳細なエラーはログファイル（`error_log`）に記録する。 |
| **バリデーションの分散** | 入力チェックのロジックが各Controller（`submit_shift.php`, `register.php`）に散在している。 | バリデーションクラスを作成し、ルールを統一管理する（例: `Validator::check($data, $rules)`）。 |

### 4.3 パフォーマンスと拡張性 (Better to Fix)
| 課題 | 詳細 | 改善提案 |
| :--- | :--- | :--- |
| **N+1問題の可能性** | 現在は目立たないが、ループ内でSQLを発行するような箇所が増えるとパフォーマンスが劣化する。 | JOINを使用した一括取得クエリを徹底する。 |
| **自動テストの欠如** | テストコードが存在しないため、機能追加時のデグレ（既存機能の破壊）検知が困難。 | `PHPUnit` を導入し、重要なビジネスロジック（給与計算、シフト重複チェック）の単体テストを作成する。 |

## 5. 推奨されるロードマップ

### フェーズ1: 足回りの強化（1週間）
1.  **環境変数の導入**: `config.php` の機密情報を `.env` に切り出し。
2.  **エラーハンドリング統一**: `try-catch` の共通化とログ出力設定。
3.  **セッション設定強化**: セキュリティヘッダーの追加。

### フェーズ2: コード構造の改善（2週間）
1.  **クラス化**: `functions.php` の関数を適切なクラス（Class）にリファクタリング。
2.  **共通部品の整備**: ヘッダー・フッター以外のUIコンポーネント化（アラート、カードなど）。

### フェーズ3: 品質保証（継続）
1.  **テスト導入**: 給与計算ロジックから単体テストを記述。
2.  **静的解析**: `PHPStan` などのツールを入れ、型エラー等を自動検知。

## 6. 総括
現行システムは「動くもの」としては完成度が高いですが、「長く使い続ける」「安全に拡張する」ためには、プロの視点でのリファクタリングが推奨されます。特にセキュリティに関わる設定情報の管理方法は、運用開始前に必ず修正すべき点です。
