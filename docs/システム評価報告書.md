# システム評価報告書

以下の観点に基づき、現状のシフト管理システムのコードベースを評価しました。
全般的に、基本的なセキュリティ対策（SQLインジェクション対策、XSS対策、CSRF対策）は実装されていますが、**マルチテナント設計とユーザー登録フローの間に致命的な不整合**が存在します。また、一部の機能に競合状態（レースコンディション）のリスクが見受けられます。

## 1. 致命的な課題 (Critical Issues)

### 1.1 アーキテクチャの不整合 (シングルテナント vs マルチテナント)
**現状:**
- データベースは `company_id` を導入し、マルチテナント（複数企業対応）構造に移行しています。
- しかし、エントリーポイントである `index.php` は `SELECT COUNT(*) FROM users` でユーザーが1人でも存在する場合、新規登録リンクを非表示にするロジックになっています。
- `register.php` は `company_id` を明示的に指定せず、デフォルト値（初期移行用企業）にユーザーを追加する挙動となっています。

**リスク:**
- 最初の1人が登録した後、**新しい企業オーナーがサインアップする導線が消失します。**
- `register_company.php` というファイルが存在しますが、画面上からの導線が不明確です。
- システムが「SaaS型（複数企業が利用）」を目指しているのか、「インストール型（1企業1サーバー）」を目指しているのかがコード上で混在しており、仕様としての致命的な欠陥となります。

### 1.2 従業員番号生成の競合状態 (Race Condition)
**ファイル:** `register_staff.php`
**現状:**
```php
$stmtMax = $pdo->prepare("SELECT MAX(company_user_id) FROM users WHERE company_id = ?");
// ...
$nextCompanyUserId = ($maxId) ? $maxId + 1 : 1;
// ... Insert処理
```
**リスク:**
- ほぼ同時に複数のユーザーが登録を行った場合、同じ `maxId` を取得し、**同じ従業員番号（company_user_id）を持つユーザーが重複して登録される**可能性があります。
- データの整合性が破壊され、給与計算やシフト管理で致命的なエラーを引き起こす原因となります。
- **対策:** トランザクションの使用（`FOR UPDATE`でのロック）、または `INSERT INTO ... SELECT ...` 構文を用いたアトミックなID採番が必要です。

## 2. セキュリティ評価 (Security Assessment)

### 2.1 ログインロックアウトの仕様 (DoSリスク)
**ファイル:** `index.php`
**現状:**
- `username` でログインを行いますが、システム上 `username` のユニーク制約は削除され（マルチテナント化のため）、同名のユーザーが複数存在する可能性があります。
- ログイン失敗時、同名のユーザーのうち「最初の1人（検索順）」に対してロックカウントを加算しています。
- **リスク:** 攻撃者が「tanaka」などの一般的な名前で総当たり攻撃を行った場合、**無関係なユーザーのアカウントがロックされる**可能性があります（Account Lockout DoS）。

### 2.2 基本的な脆弱性対策 (Good)
- **SQLインジェクション:** `PDO` とプリペアドステートメントが適切に使用されており、問題ありません。
- **XSS (クロスサイトスクリプティング):** 出力時に `h()` 関数によるエスケープが行われており、確認した範囲では適切です。
- **CSRF:** 重要なPOST処理においてトークン検証が行われています。

## 3. 保守性と品質 (Maintainability & Quality)

### 3.1 データベース定義の乖離
- `db/schema.sql` が古く、実際のデータベース構造（`company_id` カラムなど）と一致していません。
- 新規開発者が参画した際や、サーバー移転時に `schema.sql` を使ってセットアップするとシステムが動作しません。

### 3.2 責務の分離
- `launch_background_process` 関数など、バックグラウンド処理の仕組みがありますが、非同期処理のエラーハンドリングや監視体制（ログ以外）が簡易的です。メール送信失敗時などのリカバリーフローが確立されていません。

## 推奨される改善アクション

1.  **登録フローの再設計:**
    - `index.php` の登録リンク非表示ロジックを撤廃する。
    - 「新規企業登録」と「スタッフ登録（招待コード入力）」の導線を明確に分ける。
2.  **ID採番ロジックの修正:**
    - `company_user_id` 生成時にデータベーストランザクションを利用し、排他制御を行う。
3.  **ログイン仕様の変更:**
    - 同一ユーザー名でのログインを許容する場合、「企業コード + ユーザー名」または「メールアドレス」でのログインに変更し、アカウントを一意に特定できるようにする。
4.  **ドキュメントの最新化:**
    - `schema.sql` を現在のDB構造に合わせて更新する。
